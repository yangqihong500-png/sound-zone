# 05 · 初步开发方案

> 状态：v0.2 —— 用途已确认为**腾讯音乐比赛**，交付物 = **Demo 链接 + 演示视频 + 封面图**。
> 产品定义见 docs/01~04，本方案只回答"怎么建、按什么顺序建、用什么建"。

## 0. 用途已确认：TME 比赛交付

比赛只需三样交付物，这决定了整个工程策略——**一切为"评审体验"服务**：

| 交付物 | 形态 | 关键点 |
|---|---|---|
| Demo 链接 | 公开可访问的 H5（手机端优先） | 评委大概率用手机打开 → 移动端 UI 优先；加载要快，不能要注册 |
| 演示视频 | 2–3 分钟录屏 + 讲解 | 讲完整故事线：痛点 → 进域 → 点歌 → 特效 → 碎片 → 战报 → 数据飞轮 |
| 封面图 | 主视觉一张 | 比赛门面，体现"同频/域"概念 + TME 生态位 |

**工程策略：路线 A（H5 Demo）全速推进，路线 B（上架/资质）不做。** 架构仍按可演进设计，但不为运营期需求多花一天。

## 1. 关键约束与对策

### 约束 1：音乐版权与音源
- TME 不向第三方开放全曲流媒体 API，直接"基于 TME 曲库"做独立 App 在法律上不可行
- **对策：音源抽象层（MusicProvider 接口）**
  - 开发期：Audius（开放 API、可流媒体播放）、Jamendo（CC 授权）→ 曲库数万首，够做演示
  - 接口设计：`search / getTrack / getStreamUrl / getTags`，TME 源作为未来实现类预留
  - 标签体系自建（见 §4.3），不依赖音源方标签

### 约束 2：上架资质
- 音乐/电台类目小程序需《信息网络传播视听节目许可证》，App 上架应用商店同理需资质
- **对策**：演示期用 H5（可部署成公开链接，微信内可打开）；比赛/简历场景完全够用

### 约束 3：团队规模
- 假设 1–2 人（你 + 合作伙伴），其中算法/后端由你（数据科学背景）承担
- **对策**：技术选型向 Python 生态倾斜，减少语言分裂；前端用 uni-app 一套代码出多端

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 客户端 | uni-app（Vue3 + TypeScript） | 一套代码出微信小程序 + iOS/Android + H5；中文生态文档全 |
| 后端 | Python FastAPI | 与算法同语言；原生 async 支撑 WebSocket |
| 实时层 | WebSocket（FastAPI + Redis Pub/Sub） | 播放同步、点歌广播、红心特效都是推送模型 |
| 数据库 | PostgreSQL（业务数据）+ Redis（播放状态/队列/在线人数） | 队列和"当前播放"是高频读写，放 Redis |
| 文件存储 | 腾讯云 COS（或 CloudBase 存储） | 碎片图片 |
| 内容审核 | 腾讯云内容安全 API（图片/文本） | 按调用量付费，免自建 |
| 部署 | Docker + 腾讯云轻量服务器（约 ¥50/月） | 一台 2C4G 够 demo；后期再拆 |
| 曲风打标 | Essentia / PaNNs 预训练模型 + 规则 | 音频多标签分类，离线批处理 |
| 配乐模型（后期） | CLIP 式双塔（PyTorch） | 见 docs/03 |

## 3. 系统架构

```
客户端（uni-app：小程序 / App / H5）
        │  HTTPS API + WebSocket
        ▼
接入层：WS 网关 · 播放状态权威时钟 · 实时广播
        ▼
服务层（FastAPI）
  域服务    —— 建域 / 场景标签归一化 / 曲风黑名单
  队列服务  —— 点歌 / 得分排序 / 番茄钟预存队列
  碎片服务  —— 图文发布 / 审核回调 / COS 存储
  反馈服务  —— 红心收藏 / 实时特效推送 / 域后战报
        ▼
数据与算法层
  PostgreSQL · Redis · COS · 曲风打标 · 配乐模型
        ▼
外部依赖：Audius/Jamendo（音源）· 腾讯云（存储/审核）
```

**核心设计：播放同步协议**
- 服务端是每个域的"权威时钟"：`{track_id, started_at, position, queue_version}`
- 客户端进域 → WS 下发当前状态 → 本地按 `started_at + 网络延迟补偿` 对齐播放进度
- 切歌、点歌、红心均由服务端广播，客户端不自行决定顺序——天然支持"所有人听同一首"
- 演示期简化：音源用流媒体 URL，客户端各自拉流、以服务端时钟对齐（不做服务端转推，省带宽）

## 4. 核心模块拆解

### 4.1 队列状态机
```
点播 → 黑名单校验 → 时段白名单校验 ──通过──→ 活跃队列（按得分排序）
                          │不通过
                          ▼
                     预存队列（等到允许时段自动转正）
```
- 得分公式见 docs/02：`点赞×2 + 域主加成×3 − 近1h已播×1.5`
- 队列快照存 Redis，变更即广播 `queue_version+1`

### 4.2 实时特效链路
```
听众点红心 → 反馈服务写事件 → 查询当前歌曲点歌人 → WS 定向推送特效消息 → 点歌人客户端播放动效
                                        │
                                        └→ 事件落库 → 域结束后聚合生成个人战报推送
```

### 4.3 曲风标签体系（MVP 简化版）
- 冷启动不打标模型，先**人工 + 规则**：demo 曲库规模可控（数百首精选），人工打多维标签（流行/舒缓/抖音热曲/情歌/电子…）
- 同期用 Essentia/PaNNs 跑离线多标签分类，与人工标签对比校准 → 逐步自动化
- 这一步恰好是你数据科学能力的展示点，也对应 docs/04 风险表里的"标签质量"

### 4.4 碎片与数据飞轮埋点
- 每条碎片落库即三元组 `(scene_tag, image/text, track_id, ts)`，表结构预留训练导出
- 行为事件统一 `event_log` 表：点歌、红心、收藏、特效触发、收听时长 —— 战报与歌品值都从这里算

## 5. 里程碑（按 1–2 人、课余时间估算）

| 阶段 | 周期 | 产出 | 对应产品阶段 |
|---|---|---|---|
| M0 脚手架 | 第 1–2 周 | 仓库拆分（app/ + server/）、音源接入、本地播放器、WS 打通 | — |
| M1 最小闭环 | 第 3–6 周 | **1 个官方域**：实时同频收听 + 点歌队列 + 红心特效 | 阶段一 |
| M2 碎片与战报 | 第 7–9 周 | 碎片墙（图文+COS+审核）、域后战报推送 | 阶段一完整 |

### 比赛交付物工作流（与开发并行）

| 交付物 | 启动时间 | 生产方式 |
|---|---|---|
| 封面图 | M1 即可启动 | AI 生成 + 人工精修：主视觉"同频/域"概念，可出多版供选 |
| 演示视频 | M2 闭环后录制 | 先写 2–3 分钟分镜脚本（痛点 15s → 核心闭环 90s → 数据飞轮 30s → 远景 15s），录屏 + 配音 |
| Demo 链接 | M1 结束时上线第一个版本 | H5 部署到国内可快速访问的静态托管 + 轻量服务器后端；评委免注册直接进入官方域 |

**Deadline 倒排原则**：若比赛截止日早于 M2 完成时间，砍 M2 的审核/战报细化，保"进域→听→点歌→特效"四个镜头可录。

**M2 结束 = 可演示的完整故事**：进域 → 同频听 → 点歌 → 红心特效 → 发碎片 → 收战报。比赛/面试讲这条线足够。
**M4 是你的差异化**：多数产品 demo 止步于 CRUD，配乐推荐模型是数据科学背景的核心竞争力。

## 7. 主要风险与对策

| 风险 | 对策 |
|---|---|
| 两人课余开发进度失控 | M2 为第一个 Deadline 倒排；M3+ 允许砍 |
| 实时同步复杂度（延迟对齐） | 演示期容忍 ±1s 偏差；不做服务端混流 |
| 音源曲库与中文歌不匹配 | 打标时优先选风格覆盖全的曲；演示话术聚焦"机制"而非"歌单" |
| 微信小程序审核驳回（音乐类目） | 首发 H5，小程序作为加分项尝试工具类目包装 |
| 配乐模型数据量不足 | M4 用公开图文-音乐数据预训练 + 少量碎片微调，定位"可行性 demo" |
